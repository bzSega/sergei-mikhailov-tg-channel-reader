# task-0002 — Surface link-preview / web_page content in reader output

**Status:** done (2026-05-16)

## Context

User reported that posts consisting of a Telegram link-preview card (the
`webpage` media type — the kind that renders as a card with title, image, and
URL, often used together with Instant View by news / press channels) are
effectively invisible to downstream consumers of the reader output. The
example used to report the bug was a public news-channel post whose visible
body in the Telegram app comes entirely from the link preview's `description`
field; `msg.text` was empty.

Today both backends ignore the `web_page` data entirely:

- **Pyrogram (`reader.py`)** — reads `msg.text` / `msg.caption` but never
  touches `msg.web_page` (which is a separate attribute from `msg.media`). Card
  data is silently dropped.
- **Telethon (`reader_telethon.py`)** — sees `msg.media` as
  `MessageMediaWebPage` and records `media_type: "MessageMediaWebPage"`, but
  never unpacks the inner `WebPage` object. Worse: with `--text-only`, these
  posts are dropped wholesale because `msg.media is not None` — a backend
  inconsistency with Pyrogram, which keeps them.

Net effect: a card-only post arrives at the consumer with `text: ""` and no
preview data. The agent reading the JSON sees nothing useful and drops the
post — so from the user's point of view the post never existed.

## Plan

A formal plan was produced and approved in plan-mode (the plan file lives
outside the repo, under the user's local Claude state directory, and is not
committed). Outline:

1. **New JSON field** `web_page: {url, display_url, title, description, site_name}`
   on each message entry. Photo data intentionally excluded — reader is a text
   tool. The field is omitted entirely when the message has no preview, so
   existing consumers are unaffected.
2. **Synthesize `text`** from `title + "\n\n" + description + "\n\n" + url`
   (skipping any missing parts) when `msg.text` / `msg.caption` is empty but a
   `web_page` exists. Guarantees `--text-only` keeps these posts and that
   `text`-reading consumers see real content. Original text is never modified.
3. **Plain-text mode** (`--format text`) prints one extra line after the body:
   `🔗 <title> — <url>` (display_url when url is long).
4. **Comments** (`_fetch_comments` in both backends) get the same treatment so
   link-share comments are no longer dropped by the empty-text `continue`.
5. **Telethon `has_media`** is set to `false` for `MessageMediaWebPage` (and
   `media_type` is no longer emitted for that case) — aligns the two backends
   and removes the `--text-only` divergence. Only behavioural change visible
   to existing consumers; documented in CHANGELOG.
6. **Degenerate webpage variants** (`WebPageEmpty`, `WebPagePending`,
   `WebPageNotModified`, or a `WebPage` with no `url`) are skipped — the
   extraction returns `None` and the entry has no `web_page` key.

Backend-isolation convention preserved — each backend gets its own
`_extract_web_page(msg)` helper inside its own file; no shared module.

Version bump 0.9.2 → 0.9.3 in `setup.py`. CHANGELOG entry leads with a
user-friendly description, then technical bullets. CHANGELOG, commit messages,
PR title/body, and this task file stay generic — the specific channel/post
URL the user used to report the bug is not cited anywhere on disk (public
repo hygiene).

## Result / outcome

Delivered in PR #3 against `main`:

- [reader.py](../reader.py) — added `_extract_web_page` and
  `_synth_text_from_web_page` helpers; wired into the main `_fetch_channel`
  loop and `_fetch_comments`; `_print_text` now emits a `🔗 title — url`
  line after the message body when a card is present.

## Lessons

- `msg.web_page` in Pyrogram lives on the Message object **separately** from
  `msg.media`; in Telethon the same data is wrapped inside `msg.media` as
  `MessageMediaWebPage.webpage`. The two APIs disagree about whether a link
  preview is "media" — the consumer code has to pick one semantic and align
  the backends to it, otherwise filters like `--text-only` will diverge
  silently between them.
- Public-repo hygiene survived a second test: the user explicitly asked not
  to cite the specific channel/post URL they used to report the bug. The
  CHANGELOG, commit messages, PR body, and this task file all stay generic
  ("a public news channel post with an Instant View card"). The rule from
  task-0001 was already in CLAUDE.md, but having the user reinforce it
  mid-task is a useful reminder that example URLs from chat are personal
  reading material, not repo content.
- The bug had two distinct user-visible symptoms in a single root cause:
  posts disappearing entirely (when `msg.text` was empty) and posts losing
  their card metadata (when `msg.text` was non-empty). The first symptom is
  what prompted the report ("nobody will see this post"), but the second
  symptom existed silently for every Instant-View post the skill had ever
  fetched. Worth keeping in mind for future bug triage — the visible
  symptom may only be the loudest of several caused by the same defect.
