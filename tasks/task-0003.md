# task-0003 — Migrate Pyrogram backend to pyrofork to restore parsing of recent Telegram posts

**Status:** done (2026-05-16)

## Context

Right after 0.9.3 shipped, smoke-testing on a real channel surfaced a regression
that is **not** caused by 0.9.3 — it predates it, but 0.9.3's link-preview fix
made it visible. The symptom: recent posts (May 2026) come through the
Pyrogram backend with `text: ""`, `has_media: false`, no `web_page` field —
even though the same post displays fully in the official Telegram app and the
Telethon backend handles it (partially) fine.

Investigation in `pyrogram` 2.0.106 source (the only release on PyPI, frozen
since August 2023) confirmed the root cause:

- Telegram rolled out new `Message` TL constructor IDs sometime in May 2026
  (the user observed constructor IDs like `3106895567` on affected posts).
- Pyrogram 2.0.106 does **not** know these constructor IDs.
- When it receives a message encoded with one, it parses out only the trivial
  metadata (`id`, `date`, `views`, `forwards`, `edit_date`) and leaves
  `msg.message`, `msg.media`, `msg.entities`, and `msg.web_page` all as `None`.

So the 0.9.3 `_extract_web_page(msg)` helper sees `msg.web_page = None` and
returns `None` correctly — there really is no data on the parsed object, even
though the raw MTProto frame had everything. The bug is one layer below us.

This same defect was independently hit by the user in another project
(`SMTools-Alice-SMM-feedback-Monitoring`) earlier on 2026-05-16, where they
migrated from `pyrogram 2.0.106` to **`pyrofork 2.3.69`** and the empty
messages were resolved. `pyrofork` is a community-maintained drop-in fork
that ships with the current Telegram TL schema, installs into the same
`pyrogram` import namespace, and uses format-compatible session files
(no re-auth required).

## Plan

1. **`setup.py`** — swap `pyrogram>=2.0.0` for `pyrofork>=2.3.69`. `tgcrypto`
   and `telethon` deps stay. Comment in `install_requires` explains the
   reasoning so a future contributor doesn't revert it.
2. **No source changes** in `reader.py` / `tg_reader_unified.py` — pyrofork
   exposes the same `pyrogram` namespace, so `from pyrogram import Client`
   keeps working unchanged. This is the whole point of pyrofork.
3. **CHANGELOG.md** — new `[0.9.4]` entry: user-friendly lead, followed by a
   `Required user action` block with the exact `pip uninstall pyrogram -y &&
   pip install pyrofork` migration command (existing installs need to
   manually drop pyrogram because pyrofork shares the namespace and `pip`
   won't transparently switch the two).
4. **`setup-tg-reader.sh`** — diagnostic block updated: if it detects
   `pyrogram.__version__ == "2.0.106"`, it now reports it as outdated and
   prints the migration command, instead of marking it OK.
5. **`SKILL.md`, `README.md`, `README_TELETHON.md`** — install commands and
   the Library Selection table updated to say "pyrofork" instead of
   "pyrogram". Added a short note explaining why.
6. **`CLAUDE.md`** — "Current version" → 0.9.4, "Dependencies" block
   rewritten, with an explicit note **not** to add `pyrogram` back as a dep.
7. **Version bump** 0.9.3 → 0.9.4 in `setup.py`.

This task file + the task index in CLAUDE.md update last, inside the same PR
before merge, per the task-status-flip rule.

- [CHANGELOG.md](../CHANGELOG.md) — new `[0.9.4]` entry, restructured for LLM/agent consumers: explicit `Why this was broken` / `How it works after this update` / `Required user action` / `Fixed` / `Changed` / `Not changed (no regression risk)` sections. An agent reading just the CHANGELOG can determine the new public surface from "How it works" and what stays safe from "Not changed", without parsing prose.
- [tg_check.py](../tg_check.py) — `_check_backends` now detects `pyrogram == "2.0.106"`, marks the backend dict with `outdated: true` and `fix: "<migration command>"`, and surfaces the migration command in the JSON `problems` array. The "no backend installed" hint also rewritten to recommend `pyrofork`.
- [reader.py](../reader.py) and [tg_reader_unified.py](../tg_reader_unified.py) — ImportError fallback messages now recommend `pyrofork` and explicitly warn against re-installing upstream `pyrogram`.
- [setup-tg-reader.sh](../setup-tg-reader.sh) — same outdated-`pyrogram` detection logic, with the migration command printed inline.
- [SKILL.md](../SKILL.md), [README.md](../README.md), [README_TELETHON.md](../README_TELETHON.md) — install commands include the pre-emptive `pip uninstall pyrogram` step; library-selection sections updated; short explanation of why pyrofork instead of pyrogram is included where users land first.
- [CLAUDE.md](../CLAUDE.md) — `Current version` → 0.9.4; `Dependencies` block rewritten with an explicit note **not** to re-add `pyrogram`.

No source changes in `reader.py`, `reader_telethon.py`, `tg_reader_unified.py`, or `tg_state.py` beyond the user-facing error strings — pyrofork serves the `pyrogram` import namespace, so `from pyrogram import Client` keeps working unchanged.

## Lessons

- `pyrogram` on PyPI has been frozen since Aug 2023 — anyone reading a fresh "OpenClaw skill that uses Telegram MTProto" guide would naturally `pip install pyrogram` and silently inherit a parser that drops content for any post Telegram introduced after Aug 2023. The fact that 0.9.3's `_extract_web_page` looked correct in isolation, while the underlying object was already empty, is the canonical "the bug is one layer below the layer I'm staring at" trap. Cross-reference: auto-memory `reference_pyrogram_vs_pyrofork.md`.
- The fix worked because pyrofork preserves the `pyrogram` import namespace and session-file format — that compatibility surface is what made the swap a single-file change in `setup.py` instead of a fork in `reader.py`. Worth remembering for future "the maintained fork of X is Y" situations: ask whether the fork preserves the namespace before assuming the swap is invisible.
- Diagnostic JSON should expose machine-readable fields, not prose. Adding `outdated: true` + `fix: "<command>"` to `tg-reader-check` output is a small change that lets an agent surface the exact migration command to the user without needing to template-match against a localised string in a `problems` array.
- The original review caught three install-hint strings that would have undone the entire fix for any user who reads docs instead of CHANGELOG. Cross-file consistency for "install command" / "library name" / "version string" mentions deserves the same systematic sweep that the open-source-hygiene rule applies to host-local paths and secrets.
