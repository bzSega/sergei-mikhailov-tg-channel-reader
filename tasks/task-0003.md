# task-0003 — Migrate Pyrogram backend to pyrofork to restore parsing of recent Telegram posts

**Status:** in-progress (2026-05-16)

## Context

Right after 0.9.3 shipped, smoke-testing on a real channel surfaced a regression
that is **not** caused by 0.9.3 — it predates it, but 0.9.3's link-preview fix
made it visible. The symptom: recent posts (May 2026) come through the
Pyrogram backend with `text: ""`, `has_media: false`, no `web_page` field —
even though the same post displays fully in the official Telegram app and the
Telethon backend handles it (partially) fine.

Investigation in `pyrogram` 2.0.106 source (the only release on PyPI, frozen
since August 2023) confirmed the root cause:

- Telegram rolled out new `Message` TL constructor IDs sometime in May 2026
  (the user observed constructor IDs like `3106895567` on affected posts).
- Pyrogram 2.0.106 does **not** know these constructor IDs.
- When it receives a message encoded with one, it parses out only the trivial
  metadata (`id`, `date`, `views`, `forwards`, `edit_date`) and leaves
  `msg.message`, `msg.media`, `msg.entities`, and `msg.web_page` all as `None`.

So the 0.9.3 `_extract_web_page(msg)` helper sees `msg.web_page = None` and
returns `None` correctly — there really is no data on the parsed object, even
though the raw MTProto frame had everything. The bug is one layer below us.

This same defect was independently hit by the user in another project
(`SMTools-Alice-SMM-feedback-Monitoring`) earlier on 2026-05-16, where they
migrated from `pyrogram 2.0.106` to **`pyrofork 2.3.69`** and the empty
messages were resolved. `pyrofork` is a community-maintained drop-in fork
that ships with the current Telegram TL schema, installs into the same
`pyrogram` import namespace, and uses format-compatible session files
(no re-auth required).

## Plan

1. **`setup.py`** — swap `pyrogram>=2.0.0` for `pyrofork>=2.3.69`. `tgcrypto`
   and `telethon` deps stay. Comment in `install_requires` explains the
   reasoning so a future contributor doesn't revert it.
2. **No source changes** in `reader.py` / `tg_reader_unified.py` — pyrofork
   exposes the same `pyrogram` namespace, so `from pyrogram import Client`
   keeps working unchanged. This is the whole point of pyrofork.
3. **CHANGELOG.md** — new `[0.9.4]` entry: user-friendly lead, followed by a
   `Required user action` block with the exact `pip uninstall pyrogram -y &&
   pip install pyrofork` migration command (existing installs need to
   manually drop pyrogram because pyrofork shares the namespace and `pip`
   won't transparently switch the two).
4. **`setup-tg-reader.sh`** — diagnostic block updated: if it detects
   `pyrogram.__version__ == "2.0.106"`, it now reports it as outdated and
   prints the migration command, instead of marking it OK.
5. **`SKILL.md`, `README.md`, `README_TELETHON.md`** — install commands and
   the Library Selection table updated to say "pyrofork" instead of
   "pyrogram". Added a short note explaining why.
6. **`CLAUDE.md`** — "Current version" → 0.9.4, "Dependencies" block
   rewritten, with an explicit note **not** to add `pyrogram` back as a dep.
7. **Version bump** 0.9.3 → 0.9.4 in `setup.py`.
